# 配比与预算规则(Agent 用)

> 本文件说明脚本内部的确定性规则。**当用户质疑"为什么买这么多/这么少"时,
> 用这里的公式回答,不要临时改数字。**

---

## 一、配比配额是怎么算的

设 `P = 人数`,`K = 其中儿童数`:

| 角色 | 配额 | 说明 |
|---|---|---|
| **主食** | `(P - K) + 0.7 × K`,四舍五入,至少 1 | **唯一不允许打折的配额** |
| 饮料 | `P < 6` 且未提及饮料 → 0;否则 `0.7 × P` | 很多团队自带水,不强求 |
| 小食 | `P / 3`;偏好含「饱腹/可分食」时提到 `P / 2` | 四舍五入,至少 1 |
| 甜品 | 默认 0;下午茶或有儿童时 `P / 3` 或按儿童数 | 明确提到甜品才配 |

**为什么主食配额是硬的**:团餐最常见的翻车就是「小食买一堆、主食不够分」。
官方在 `query-meals` 的说明里也给出过团餐搭配建议(按人均预算组合
汉堡+小食+饮料),本规则与其思路一致。

### 加分项(软偏好如何影响选择)

| 偏好 | 效果 |
|---|---|
| `low_calorie` | 单件热量越低得分越高(250 kcal 以上开始扣分) |
| `high_protein` | 单件蛋白质越高得分越高;**素食场景下自动忽略此项** |
| `low_sodium` | 单件钠越高扣分 |
| `filling` | 主食/套餐/小食加分 |
| `shareable` | 拼盘、套餐、鸡翅类加分 |
| `coffee` | 含咖啡/美式/拿铁字样的饮料加分 |
| `dessert` | 甜品类加分 |
| `refreshing` | 柠檬/红茶/绿茶/无糖/美式类饮料加分 |

## 二、求解器在优化什么

目标函数(**分数越低越好**):

```
score = 成本
      + 配额缺口罚分
      - 软偏好加分
      - 预算利用率加分
      + 多样性惩罚
```

| 项 | 数值 | 为什么 |
|---|---|---|
| 主食缺口 | 6000 分/件(≈60 元) | 权重不足会出现「14 份冰淇淋配 2 个汉堡」 |
| 小食缺口 | 1200 分/件 | 软配额,预算紧时允许不足 |
| 饮料缺口 | 400 分/件 | 同上 |
| 甜品缺口 | 300 分/件 | 同上 |
| 软偏好 | 1 分 ≈ 1.2 元 | 让「好搭配」压过「纯凑便宜」 |
| 多样性惩罚 | 同类中单品的占比超过上限起罚 | 上限:主食 50%、小食 60%、饮料 60%、甜品 60% |
| **预算利用率** | 成本的 35% | **团餐预算通常不结转,剩太多等于白批** |

**求解方式**:可行性过滤 + 随机多起点局部搜索。相同随机种子下结果**完全可复现**。
搜索强度由 `--effort` 控制(默认 48 次重启)。

## 三、被排除的条目(不会进清单)

| 类别 | 原因 |
|---|---|
| 蘸酱、调味酱、餐具、纸巾 | 不占餐食配额;否则求解器会把剩余预算全换成几十包酱(实测踩坑) |
| 瓶装饮用水(纯悦/矿泉水等) | 不占饮料配额,避免把预算耗在水上 |
| 售罄商品 | `calculate-price` 查不到价格的编码 |
| 违反硬性忌口的商品 | `--avoid` 指定 |

## 四、约束让位规则(重要,必须如实告知用户)

若按忌口过滤后**主食池为空**,脚本会按下列顺序逐条放宽约束,
并**在 `plan.relaxations` 里逐条记录**:

```
不吃辣 → 不吃蛋 → 乳制品不耐受 → 不吃鱼 → 不吃猪 → 不吃牛 → 不吃鸡 → 素食
```

原则是:**宁可少满足一条约束,也不能给出违反用户明确声明的方案。**
但只要发生了让位,你就**必须**把 `relaxations` 原文转述给用户,请他人工复核。

## 五、预算收敛规则(门店实价高于估算时)

本地"单价 × 数量"只是估算。脚本会用 `calculate-price` 回算,若超预算则自动削减:

```
削减顺序:甜品 → 小食 → 饮料 → 超出人数的多余主食
```

每一轮削减后都会**重新核价**,直到回到预算内。
**主食是最后防线**:削减到低于人数即停止,并在 `warnings` 里说明,把决定权交回用户。

被削减的动作会汇总成一条 `auto_cut` 提示,例如
`为回到预算内,已减少:苹果片×2`。

## 六、营养数据的可信度

| 情况 | 脚本行为 | 你要怎么说 |
|---|---|---|
| 单品命中官方营养表 | 直接采用 | 可正常呈现 |
| 套餐/含多件商品 | 用 `query-meal-detail` 拆解默认组成后累加 | 说明是"按官方默认组成累加" |
| 拆解后仍有子项没匹配到 | 累加已匹配部分,并在 `warnings` 提示 | 说明"实际值会略高" |
| 完全没数据 | **不按 0 计入**,单独统计 | **必须**说明"营养合计为下限值,偏低" |
| 主食全部无数据 | 触发 `nutrition_mains_missing` 告警 | **必须**强调数值严重偏低,不可当真 |
| 离线模式(`--offline`) | 无法调 `query-meal-detail`,套餐营养缺失 | 说明离线演示不含套餐拆解 |

**任何情况下都不要把缺失的营养当 0 呈现给用户。**
